## Reporting policy and transition guard
The selected public policy is one conversational Korean status card per task, edited in place. Observe every 10s; ordinary edits are at least 30s apart. Ordinary meaningful notices have a 20-minute minimum separation; file saves, routine test failures/retries and unchanged evidence never create ordinary notices. Worker termination and actual coordinator verification are immediate transitions, coalesced into one notice when within 30s. Never say verification started before the coordinator explicitly enters it. Input waits, blocking failure/cancellation and verified completion notify immediately once per episode. No new evidence for 20min creates one warning per episode; observation loss is not worker failure. Recovery rearms the warning. Templates are deterministic and introduce no model calls.

This is a launcher + launchd-owned supervisor workflow, not an automatic gateway router or a hook on arbitrary raw CLI commands. No gateway restart, worker migration or state reset.

The supervisor, not a transient shell, owns reporting. `start` normally stays attached as a waiter: run it using terminal `background=true, notify_on_complete=true` so its eventual success/attention returns to the coordinator. launchd in the logged-in Mac GUI domain restarts a crashed monitor. A normal 7200s bridge lifetime renews without stopping monitoring; durable failure budget is 5, with 10/30/60/120s backoffs, plus at most 5 launchd process starts per run. Exhaustion or invalid state ends in `attention`, preserves pending delivery and causes the waiter to exit74. Do not reset budgets or restart the worker. `supervision.json` and `launch-budget.json` under the per-run state directory are the recovery record. Mac logout/reboot requires reattaching with the identical `start` command; these dynamically registered per-run jobs are not system boot services. If Discord is unreachable, do not claim that an alert was delivered. The coordinator owns the background completion event and follow-up recovery.

Uncertain delivery is retried only with GET-only server-journal recovery when an authenticated response already bound an exact message ID. Missing binding remains uncertain and requires investigation; never blind resend, clear state or fabricate an ACK. Final success requires the verified final card and notice ACKs, pending0, stoppedtrue and supervisor finished. The collector uses bounded metadata checks during unchanged working periods with a 60s forced full collection; test evidence, public snapshots and coordinator verification retain exact collection.
